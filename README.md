# CauseMotion

> 로봇이 멈출 때마다, 그것이 **환경을 고칠 일**인지 **로봇이 배울 일**인지 가려서 처리합니다.
> 같은 문제가 다시 생기지 않게 하고, 학습 비용은 배울 일에만 씁니다.

CauseMotion은 건물 서비스 로봇(배송·안내·순찰)의 **현장 회복 엔진**입니다.
로봇이 멈추고 사람이 원격으로 개입할 때마다 그 원인(**Cause**)을 판정하고,
원인에 맞는 조치로 로봇이 다시 움직이게(**Motion**) 합니다.

---

## 왜 필요한가

건물 서비스 로봇은 바뀐 환경에서 반복해서 멈춥니다. 지금은 운영자가 원격으로 구출하고 넘어가거나,
최근에는 이 개입 기록을 **그대로 학습 데이터로 쓰는** 흐름이 늘고 있습니다.

하지만 로봇이 멈추는 원인 대부분은 학습으로 해결되지 않습니다.

| 원인 | 예시 | 학습으로 해결되나 |
|---|---|---|
| 일시적 원인 | 지나가는 사람 무리, 잠시 놓인 카트 | 아니요 — 기록만 남기면 됨 |
| 지도 낡음 | 가구 재배치, 행사, 임시 칸막이 | 아니요 — 해당 구역 지도를 고쳐야 함 |
| 센서·보정 | 카메라·라이다 장착 위치 틀어짐 | 아니요 — 보정해야 함 |
| 시설 연동 | 엘리베이터·출입 게이트 응답 실패 | 아니요 — 시설을 고쳐야 함 |
| **정책 부족** | 붐비는 복도에서 반복되는 회피 실패 | **예 — 이것만 학습 대상** |

원인이 정책 부족이 아닌데 학습하면 재발은 줄지 않고 비용만 늘며,
엉뚱한 데이터가 정책을 오히려 나쁘게 만들 수 있습니다.

## 어떻게 동작하나

```
멈춤 · 원격 개입
      │
      ▼
 원인 판정 ── 근거 7종 → 원인 후보 · 확신도
      │
      ├──▶ 축 1 · 환경을 고칠 일 ──▶ 지도 부분 갱신 · 구역별 주행 설정 · 보정/시설 티켓
      │                              (학습에 넣지 않음)
      │
      └──▶ 축 2 · 로봇이 배울 일 ──▶ 선별 → 원격조정 기록 검수 → 표적 학습 → 전후 검증
                                     (골라서 학습)
      │
      ▼
 재평가 · 회복 장부 ── 재발 확인 → 다음 판정의 근거
```

### 축 1 · 환경 적응

| 기능 | 하는 일 |
|---|---|
| 변화 감지 | 기준 지도와 주행 기록을 비교해 고정 변화(가구·칸막이)와 일시 변화를 구분 |
| 지도 부분 갱신 | 바뀐 구역만 지도를 고침 (전체 재제작 불필요) |
| 구역별 주행 설정 조정 | 회피 실패가 반복되는 구역에서만 여유 거리·속도를 조정하고 재발로 확인 |
| 보정·시설 티켓 | 센서 틀어짐은 보정 요청, 엘리베이터·게이트 문제는 시설 담당 티켓 |

### 축 2 · 원격조정 학습

| 단계 | 하는 일 |
|---|---|
| 선별 | 원인 판정이 '정책 부족'인 개입만 학습 후보로 보냄 |
| 검수 | 머뭇거림·불필요한 동작·센서 시간 어긋남이 있는 원격조정 기록 제외 |
| 표적 학습 | 해당 상황 유형(예: 붐비는 복도 교차)만 추가 학습 (HG-DAgger 방식) |
| 학습 후 검증 | 같은 상황 유형의 전후 성공률 비교, 다른 상황 성능 유지 확인 |

### 원인 판정

7가지 근거로 원인 후보와 확신도를 냅니다.

> 장소 반복 · 시간 반복 · 로봇 간 비교 · 변화 점수 · 센서 상태 · 시설 신호 · 일시 장애물

| 확신도 | 처리 |
|---|---|
| 높음 | 조치 제안, 운영자 한 번 승인 후 실행 |
| 중간 | 싸고 되돌릴 수 있는 조치부터 실행·관찰 |
| 낮음 | 판정 보류, 진단 실험(다른 시간대 재주행, 다른 로봇 투입, 보정 점검) |

**설계 원칙**

- 정책 부족은 '나머지'로 판정하지 않습니다. 같은 상황 유형에서 반복된다는 적극적인 근거가 있어야 학습으로 보냅니다.
- 싸고 되돌릴 수 있는 조치는 낮은 확신에서도 먼저 시도하고, 학습 데이터 투입에는 가장 강한 근거를 요구합니다.
- 지도 갱신 전에는 반드시 센서 상태를 확인합니다. 틀어진 센서로 지도를 갱신하면 지도가 오염됩니다.
- 재발하면 다음 원인 후보로 넘어갑니다.

### 회복 장부

**변화 – 장애 – 개입 – 원인 – 조치 – 비용 – 재발**을 연결해 기록합니다.
어떤 조치가 실제로 재발을 줄였는지 보여주고, 다음 판정의 근거가 됩니다.

## 예시

| | 사례 A · 축 1로 처리 | 사례 B · 축 2로 처리 |
|---|---|---|
| 상황 | 행사로 로비 소파와 안내판이 옮겨진 날 | 점심시간마다 같은 복도에서 사람 무리를 피하지 못함 |
| 장애 | 로비에서 위치 신뢰도 하락, 40초 정지 | 같은 복도에서 2주간 7회 정지 |
| 근거 | 로비 고정 변화 감지, 같은 날 다른 로봇 2대도 유사 증상 | 지도·센서·시설 정상, 특정 시간대·상황에서 여러 로봇이 반복 |
| 판정 | 지도 낡음 (확신도 중간) | 정책 부족 (확신도 높음) |
| 조치 | 로비 구역만 지도 부분 갱신, 학습에서 제외 | 기록 7건 중 검수 통과 5건으로 '붐비는 복도 교차' 표적 학습 |
| 재평가 | 같은 구역 재주행에서 재발 없으면 종결 | 다음 2주 같은 상황 성공률 비교, 다른 구역 성능 유지 확인 |

> 위 사례는 설명용 가상 시나리오입니다.

## 아키텍처

```
입력 어댑터   2D 시뮬 │ 3D 시뮬(Gazebo) │ 로그 재생·변환기 │ 실제 로봇
                 │
                 ▼  토픽 계약
      /scan  /odom  /amcl_pose  /tf  /cmd_vel  /map  navigate_to_pose
                 │
                 ▼
   장애 감지 → 원인 판정 → 축 1 / 축 2 → 회복 장부 → 진단 리포트
```

모든 모듈은 로봇이 가상인지 실제인지 모릅니다. 입력은 항상 정해진 ROS 2 토픽(토픽 계약)으로 들어오고,
공개 데이터와 운영사 로그도 변환기를 거쳐 같은 형식이 됩니다.
**입력 어댑터만 바꾸면 같은 코드가 2D 시뮬, 3D 시뮬, 실제 로봇에서 동작합니다.**

## 디렉터리 (예정)

| 경로 | 내용 |
|---|---|
| `cm_contracts/` | 토픽 계약, 메시지 정의 |
| `cm_sim2d/` | 2D 시뮬 어댑터 |
| `cm_sim3d/` | 3D 시뮬(Gazebo) 어댑터 |
| `cm_detector/` | 장애 감지, 장애 전후 클립 저장 |
| `cm_diagnosis/` | 원인 판정 |
| `cm_env/` | 축 1 · 환경 적응 |
| `cm_learn/` | 축 2 · 원격조정 학습 |
| `ledger/` | 회복 장부 DB, 진단 리포트 생성 |
| `scenarios/` | 시뮬 독립 시나리오 (구역, 변화 주입, 시드) |
| `tools/` | 공개 데이터·운영사 로그 변환기 |

## 검증 방법

시뮬레이션에서는 변화를 일부러 넣기 때문에 **원인 정답이 자동으로 생깁니다.**
같은 변화 순서로 세 방식을 같은 예산(원격조정 시간, 계산 시간)으로 비교합니다.

| 방식 | 내용 |
|---|---|
| A | 모든 개입을 학습에 사용 |
| B | 정기 지도 재제작을 포함한 고정 점검 |
| **C** | **CauseMotion — 원인 판정 후 두 축 처리** |

| 지표 | 측정 방법 |
|---|---|
| 재발률 | 같은 구역·같은 원인의 개입이 조치 후 다시 발생한 비율 |
| 판정 정확도 | 시뮬 원인 정답·라벨 대비 일치율 (확신도별) |
| 학습 효율 | 같은 학습 데이터 양 대비 목표 상황 성공률 향상 |
| 학습 데이터 오염률 | 학습에 들어간 개입 중 실제로는 비정책 원인이었던 비율 |
| 회복 비용 | 원격조정 시간, 계산 비용, 지도 갱신 횟수를 분리 측정 |
| 일반화 | 개발에 쓰지 않은 구역·변화·시드에서 반복 평가 |

**목표 (잠정)**

- 확신도 '높음' 판정 일치율 85% 이상, 전체 70% 이상
- 같은 예산에서 방식 A보다 재발률 30% 이상 낮음

> 시뮬레이션의 원인 분포는 우리가 정하는 값이므로, "실제 개입 중 비정책 원인이 상당하다"는 가설은
> 시뮬로 증명할 수 없습니다. 이 부분은 운영사 로그 진단으로 확인합니다.

## 로드맵

- [ ] **1단계 · 2D 시뮬** — 5가지 원인 주입, 장애 감지, 원인 판정 v1, 축 1·2, 세 방식 비교 실험
- [ ] **2단계 · 3D 시뮬** (Gazebo Harmonic) — 2D 시나리오 재현, 카메라 기반 원격 개입 화면
- [ ] **3단계 · 실제 로봇** (이륜 차동구동) — 실제 센서 환경에서 검증, 시뮬-실제 차이 측정
- [ ] **운영사 로그 진단** — 로그만으로 만드는 건물 단위 개입 원인 진단 리포트

**범위에서 제외**: 관제 플랫폼 전체(작업 배정·경로 관리), 지도 제작 기술 자체,
새로운 자율주행 알고리즘 개발, 완전 자율 원인 판별
